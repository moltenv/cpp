# Урок 5. Локальная LLM: llama.cpp, Hugging Face и HTTP

## Цель занятия

Установить на своём ноутбуке `llama-server` из проекта **llama.cpp**, скачать лёгкую текстовую модель с Hugging Face и показать работающий запрос и ответ. Затем подключить модель к небольшому C++-приложению: на прошлом уроке оно готовило JSON-запрос, теперь будет отправлять его по HTTP и разбирать результат.

Схема: **C++-клиент → HTTP + JSON → llama-server → GGUF-модель → ответ клиенту**. Сервер и клиент — отдельные процессы. Hugging Face нужен для получения весов; после скачивания модель работает локально. Платный API и ключ для приведённых моделей не нужны.

## 1. Как выбрать модель

**llama.cpp** выполняет инференс, **llama-server** предоставляет HTTP API и веб-интерфейс, а **модель** содержит веса нейросети. Для этого занятия скачиваем готовый файл **GGUF**. Для обычного диалога выбираем вариант **Instruct**. Квантование уменьшает размер весов за счёт точности их представления; начните с **Q4_K_M**.

| Модель на Hugging Face | Размер файла Q4_K_M, примерно | Предлагаемый сценарий |
| --- | --- | --- |
| [Qwen2.5-0.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-0.5B-Instruct-GGUF/tree/main) | 491 МБ | **Основной вариант**: короткие ответы и простая классификация |
| [SmolLM2-360M-Instruct, GGUF от bartowski](https://huggingface.co/bartowski/SmolLM2-360M-Instruct-GGUF/tree/main) | 271 МБ | Ещё меньший вариант для коротких запросов на английском |
| [Qwen2.5-Coder-0.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-Coder-0.5B-Instruct-GGUF/tree/main) | 491 МБ | Небольшие фрагменты C++ и простые сообщения компилятора |
| [Qwen2.5-1.5B-Instruct](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct-GGUF/tree/main) | 1,12 ГБ | Дополнительный эксперимент, если меньшая модель уже работает и хватает ресурсов |

Рекомендация для занятия: **Qwen2.5-0.5B-Instruct Q4_K_M на CPU**. Ориентируемся на обычный учебный ноутбук без дискретной видеокарты. Модель 1.5B и ускорение на GPU не нужны для сдачи. Сценарии в таблице — предложения для эксперимента, качество нужно проверить на собственных примерах.

Размер файла не равен потреблению оперативной памяти: дополнительно нужны память для контекста и рабочие буферы. Начните с контекста **1024 токена**, ответа **64 токена**, двух потоков CPU и одного запроса одновременно. На ноутбуке с 4 ГБ RAM закройте тяжёлые приложения и начните с 360M или 0.5B; 8 ГБ дают больше запаса. Это ориентиры для первого эксперимента, скорость и доступная память зависят от конкретного ноутбука. Не требуется получать ответ за заданное число секунд.

## 2. Установка llama-server

Основной способ для **Linux, Windows и macOS — скачать исходники через Git и собрать сервер через CMake**. Это также практика инструментов урока 4. Устанавливайте инструменты и храните модели вне каталога сдаваемого задания.

### Подготовить инструменты

Нужны Git, CMake и компилятор C/C++. Сам `git clone` только скачивает исходники, установку компилятора он не заменяет.

**Linux (Ubuntu / Debian):**

```bash
sudo apt update
sudo apt install git cmake build-essential libcurl4-openssl-dev
```

Пакет libcurl с заголовками пригодится и для C++-клиента. В других дистрибутивах установите аналогичные пакеты через свой пакетный менеджер.

**Windows:** установите [Git for Windows](https://git-scm.com/downloads/win) и [Visual Studio Build Tools](https://visualstudio.microsoft.com/downloads/) с нагрузкой **«Разработка классических приложений на C++»** (Desktop development with C++), Windows SDK и компонентом **C++ CMake tools for Windows**. Откройте **Developer PowerShell for VS** из меню «Пуск» и выполняйте дальнейшие команды там. Если CMake не установлен вместе с Build Tools, установите его с [cmake.org](https://cmake.org/download/) и добавьте в PATH.

**macOS:** установите инструменты компилятора:

```bash
xcode-select --install
```

Установите CMake с [cmake.org](https://cmake.org/download/) или через Homebrew: `brew install cmake`. Git доступен после установки Command Line Tools.

Проверьте инструменты на своей ОС:

```bash
git --version
cmake --version
```

### Сборка из исходников через CMake

Следующие команды одинаковы для Bash/Zsh на Linux/macOS и Developer PowerShell на Windows. Выполните их в каталоге, где хотите хранить инструменты:

```bash
git clone https://github.com/ggml-org/llama.cpp.git
cd llama.cpp
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DLLAMA_OPENSSL=OFF
cmake --build build --config Release --target llama-server -j 2
```

`-j 2` ограничивает сборку двумя параллельными задачами. Если ноутбуку не хватает памяти при сборке, используйте `-j 1`. На Windows с генератором Visual Studio конфигурацию Release выбирает `--config Release`.

Проверка из каталога `llama.cpp` на **Linux/macOS**:

```bash
./build/bin/llama-server --version
```

На **Windows с генератором Visual Studio**:

```powershell
.\build\bin\Release\llama-server.exe --version
```

При другом генераторе путь может отличаться, например `build/bin/llama-server.exe` для Ninja. Найдите созданный файл в каталоге `build`. Сервер после сборки не добавляется в PATH: запускайте его по указанному пути.

Сборку под конкретный GPU можно настроить по [официальной инструкции](https://github.com/ggml-org/llama.cpp/blob/master/docs/build.md). Для воспроизводимости запишите в отчёт результат `llama-server --version`, а при сборке из исходников — также `git rev-parse HEAD` в каталоге llama.cpp.

### Альтернатива: готовые бинарные файлы

Если сборка занимает слишком много времени, скачайте архив под свою ОС и архитектуру из [релизов llama.cpp](https://github.com/ggml-org/llama.cpp/releases), распакуйте его и найдите `llama-server` (`llama-server.exe` на Windows). Для первого запуска выбирайте CPU-вариант, если не уверены в поддержке своего GPU. Сохраните рядом необходимые библиотеки из архива. На macOS с Homebrew можно также выполнить `brew install llama.cpp`.

## 3. Скачать веса и запустить сервер

На странице выбранной модели откройте **Files and versions** и скачайте файл с `Q4_K_M` в имени (регистр зависит от репозитория). Для основного варианта это `qwen2.5-0.5b-instruct-q4_k_m.gguf`. Не скачивайте весь репозиторий со всеми квантованиями.

Создайте каталог `models` внутри скачанного каталога `llama.cpp` и положите туда файл. Далее команды выполняются из каталога `llama.cpp`. В первом терминале на **Linux/macOS**:

```bash
./build/bin/llama-server \
  -m models/qwen2.5-0.5b-instruct-q4_k_m.gguf \
  --alias local-model \
  -c 1024 -ngl 0 -t 2 -np 1 \
  --host 127.0.0.1 --port 8080
```

На **Windows с генератором Visual Studio**, в Developer PowerShell, выполните одну строку:

```powershell
.\build\bin\Release\llama-server.exe -m models/qwen2.5-0.5b-instruct-q4_k_m.gguf --alias local-model -c 1024 -ngl 0 -t 2 -np 1 --host 127.0.0.1 --port 8080
```

Если использовали готовые бинарные файлы или другой генератор, замените путь к серверу на свой. При установке через Homebrew можно использовать имя `llama-server`. Переносы через `\` в первом примере предназначены для Bash/Zsh.

`-m` — путь к весам, `--alias` — имя модели в API, `-c` — размер контекста, `-ngl 0` — запуск без переноса слоёв на GPU, `-t 2` — два потока CPU, `-np 1` — один слот для обработки запросов. На Apple Silicon со сборкой, поддерживающей Metal, можно дополнительно попробовать `-ngl 99` и сравнить время ответа. При нехватке памяти уменьшите модель или контекст.

Оставьте этот терминал открытым. После загрузки откройте **http://127.0.0.1:8080** и задайте вопрос в веб-интерфейсе. Чтобы сменить модель, остановите сервер через `Ctrl+C` и запустите его с другим файлом в `-m`; псевдоним `local-model` можно оставить тем же.

## 4. Первый HTTP-запрос

Во втором терминале проверьте готовность сервера:

```bash
curl -i http://127.0.0.1:8080/health
```

Готовый сервер возвращает HTTP 200 и `{"status":"ok"}`. Во время загрузки возможен HTTP 503 — дождитесь окончания загрузки.

В каталоге урока есть [request.example.json](request.example.json). Скопируйте его в рабочий каталог или укажите путь к файлу:

```bash
curl --fail-with-body --max-time 180 \
  http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  --data-binary @request.example.json
```

На Windows используйте `curl.exe` и выполните команду одной строкой. Файл запроса сохраняйте в UTF-8. Если установленный curl не знает `--fail-with-body`, используйте `-i` и проверьте HTTP-статус вручную.

В ответе найдите `choices[0].message.content` — это текст модели. Поле `model` запроса совпадает с `--alias local-model`. `stream: false` означает один JSON-ответ целиком; `max_tokens` ограничивает длину генерации. Точный текст ответа может меняться от запуска к запуску.

### Токены и общий бюджет контекста

Модель читает текст **токенами**: это могут быть слова, части слов, знаки пунктуации или другие фрагменты. Например, «Привет», `hello` и `std::vector<int>` разбиваются по-разному; результат зависит от токенизатора модели. **Токен не равен слову, символу или байту.** `std::string::size()` считает байты, поэтому проверять контекст по длине строки или числу слов неправильно.

У модели ограничено окно контекста. В нашем запуске **`-c 1024 -np 1`** задаёт бюджет 1024 токена для одного диалога: вся переданная история, системное сообщение, служебные токены шаблона чата **и генерируемый ответ** должны помещаться вместе. **1024 — осознанно небольшое учебное значение**: оно снижает требования к памяти ноутбука и позволяет быстрее увидеть заполнение контекста. Современные модели обычно поддерживают гораздо большее окно; его максимальный размер смотрите в карточке модели. Фактический размер для нашего запуска задаёт параметр сервера `-c`.

`max_tokens = 64` ограничивает длину генерируемого ответа. Сам параметр не бронирует часть контекста: **мы оставляем запас** до 64 токенов под ответ, проверяя в клиенте условие:

```text
input_tokens + max_tokens <= 1024
```

Перед генерацией отправьте **тот же JSON-запрос со всей историей** на endpoint подсчёта токенов. Например, используя файл из раздела 4:

```bash
curl --fail-with-body --max-time 10 \
  http://127.0.0.1:8080/v1/chat/completions/input_tokens \
  -H "Content-Type: application/json" \
  --data-binary @request.example.json
```

Ответ имеет вид `{"object":"response.input_tokens","input_tokens":57}`. Число здесь иллюстративное: сервер считает вход с учётом токенизатора и шаблона чата, без генерации ответа. Повторно прибавлять системное сообщение и служебные токены к `input_tokens` не нужно. Это расширение llama-server; если старая сборка возвращает 404, обновите сервер. [Описание endpoint](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-v1chatcompletionsinput_tokens-token-counting).

После обычного запроса на `/v1/chat/completions` смотрите объект **`usage`** рядом с `choices`, например:

```json
"usage": {
  "prompt_tokens": 57,
  "completion_tokens": 32,
  "total_tokens": 89
}
```

`prompt_tokens` — фактическое число токенов входа, `completion_tokens` — сгенерированного ответа, `total_tokens` — их сумма **для этого запроса**. Ответ может быть короче `max_tokens`. Это не накопительный счётчик диалога: в следующий запрос войдут также сохранённый ответ и новая реплика, поэтому его вход нужно считать заново.

## 5. Идеи простого взаимодействия

Выберите **один** сценарий. Достаточно короткого ввода и понятного вывода.

| Идея | Что делает программа | Что показать |
| --- | --- | --- |
| **Чат с памятью** | Читает реплики из терминала и хранит историю `messages` | «Меня зовут Анна» → «Как меня зовут?»; команда `/reset` очищает историю |
| **Краткий пересказ** | Принимает небольшой текст и просит три основных пункта | Свой абзац и полученный пересказ; сравнение с исходным смыслом |
| **Классификатор обращений** | Просит выбрать `учёба`, `быт` или `другое` | Несколько однозначных примеров и один спорный; проверка допустимости ответа |
| **Помощник по C++** | Принимает короткий код или ошибку компилятора и просит объяснение | Пример с пропущенным `;` или забытым исходником в CMake; проверка совета компилятором |
| **Из текста в JSON** | Просит преобразовать «Купить молоко, приоритет высокий» в объект с `title` и `priority` | Разбор результата через `nlohmann::json`, проверка полей и понятная ошибка при плохом ответе |

Для первого проекта на слабом ноутбуке рекомендуем **классификацию в одну категорию** или **пересказ одного абзаца в одно предложение**: один короткий запрос и короткий ответ. Не требуйте от модели сложных рассуждений, большого кода или длинных документов. Для знакомства с устройством чата выберите **чат с памятью**: историю хранит клиент и передаёт заново при каждом запросе. Управление её размером описано в продолжении задания ниже.

Для JSON-сценария отличайте внешний JSON ответа HTTP API от текста внутри `message.content`: этот текст нужно разбирать отдельно. Просьба «верни JSON» не гарантирует корректные данные. Для маленькой модели полезно показать и удачный пример, и ошибку. Полноценный агент с инструментами для этого задания не требуется.

6. В README опишите ноутбук (ОС, процессор, RAM и использование GPU), ссылку на модель, имя GGUF-файла, квантование, версию сервера, команды сборки и запуска. Приложите три примера своего сценария, включая один неудачный или пограничный, и кратко оцените ответы.

### Продолжение задания: история и контроль контекста

Добавьте последовательный ввод реплик в CLI. Храните историю в **`std::vector<Message>`**, где `Message` содержит строки `role` и `content`; при отправке преобразуйте вектор в JSON-массив `messages`.

1. Перед генерацией добавьте текущую реплику `user` и отправьте подготовленный запрос на `/v1/chat/completions/input_tokens`. Проверьте HTTP-статус, JSON и неотрицательное целое поле `input_tokens`; при ошибке подсчёта не запускайте генерацию.
2. Пока `input_tokens + max_tokens > 1024`, удаляйте **самую старую завершённую пару `user`–`assistant`** и считайте вход заново. Сохраняйте системное сообщение (если оно есть) и текущую реплику пользователя. Если старых пар уже нет, а запрос всё ещё велик, предложите сократить ввод; не отправляйте его модели.
3. Когда запрос помещается, отправьте его на `/v1/chat/completions` и добавьте полученный текст в историю как `assistant`. При ошибке генерации уберите неподтверждённую текущую реплику, чтобы в истории не оставалась незавершённая пара.
4. После каждого успешного ответа выводите статистику из `usage`: например, `Вход: 57, ответ: 32, всего: 89 / 1024`. Проверяйте наличие и тип полей, не подменяйте отсутствующие значения нулями. При сокращении истории сообщайте, сколько пар удалено.

На разборе покажите несколько ходов с ростом `prompt_tokens`, удаление старой пары при заполнении контекста и отказ для одного слишком длинного сообщения. Размер контекста в клиенте должен совпадать с `-c` сервера; для этой лабораторной используйте 1024 и `max_tokens = 64`. Минимальный `http_demo` остаётся примером одного запроса — историю добавляете самостоятельно.

### Как подключить HTTP к проекту урока 4

Для libcurl в CMake используются `find_package(CURL REQUIRED)` и `target_link_libraries(<цель> PRIVATE CURL::libcurl)`. Нужна установленная библиотека с заголовками; одного исполняемого файла `curl` недостаточно. На Linux обычно требуется пакет разработки libcurl, на Windows можно использовать vcpkg и указать его toolchain при конфигурации CMake.

В HTTP-функции передайте тело `request.dump()`, заголовок `Content-Type: application/json` и соберите тело ответа через callback. После `curl_easy_perform` проверьте отдельно транспортный результат и HTTP-статус (`CURLINFO_RESPONSE_CODE`). Только после успешного статуса разбирайте JSON и проверяйте вложенную структуру. Освобождайте ресурсы libcurl и список заголовков на всех путях выхода; здесь пригодится RAII из урока 2.

Значение `context_size` из конфигурации клиента само по себе не меняет контекст уже запущенного сервера: размер задаётся его параметром `-c`. Настройки генерации, например `temperature` и `max_tokens`, передавайте в запросе.

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Сервер не находит модель | Путь в `-m`, рабочий каталог, завершилось ли скачивание |
| Порт занят | Выберите другой `--port` и измените адрес в клиенте |
| HTTP 503 | Модель ещё загружается; проверьте журнал сервера |
| Не хватает памяти или очень медленно | Модель 360M или 0.5B, контекст 512–1024, ответ 32–64 токена, один слот; закройте тяжёлые приложения |
| Ответ обрывается | Проверьте `max_tokens` и длину истории относительно контекста |
| Клиент получает JSON, но не текст | Проверьте `choices`, непустой массив, `message` и строковое `content` |


ИИ разрешён для помощи со сборкой, HTTP и JSON. На разборе нужно уметь объяснить свой код и проверить рекомендации модели на конкретном примере.
